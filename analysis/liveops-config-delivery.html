Đường đi của cấu hình từ xa: Ping, delta theo version, SQLite và CDN

Config live-ops xuống client qua kênh nào, lưu ở đâu, làm mới khi nào và client xử lý ra sao khi lệch version, mất mạng hoặc file hỏng.

📡 LiveOpsPingHttpCommand (Finish, ProcessSettings, ProcessUserData)RegisterHttpCommand, UpdateUserProgressHttpCommandTimeHelper.SendPing, BackendHttpService*Manager.UpdateInfo + *ConfigHelper (ServerEventConfig / UserEventConfig)EventDependencyManager, MissionEventsHelperRemoteConfigManager (remote levels), SlbMoveConfigHelperRemoteRoyalBundleManager, ProfileSkinBundleManager, RoyalBundleManager, LevelManager (episode bundle)DatabaseService: SQLite app_pFiles/App và app_pFiles/U_<userid>
Kết luận: Royal Match dùng mô hình server quyết định, client giữ cache: mọi event mang ConfigVersion trong *Info của Ping/UpdateUserProgress, client báo lại tới 50 version đang giữ nên server chỉ gửi JSON khi lệch; cache nằm trong SQLite và 26 file default trong Resources làm lưới an toàn. Nội dung nặng (level vá, bundle, bảng SLB, giá supercharge) đi CDN riêng có ETag và checksum. Thiết kế tiết kiệm và chịu offline tốt; điểm trừ là config Seasonal Card Collection (~25,7 nghìn ký tự) bị gửi lại ở mọi response và có tới 3 luồng server + 6 file CDN độc lập nên khó quan sát tập trung.

Tóm tắt

  • Ba luồng server mang config: Register (lần đầu hoặc đổi user), Ping (TimeHelper.SendPing lúc AppStart/AppResume) và UpdateUserProgress (mỗi lần bắt đầu, thắng, thua level). Chỉ Ping mang ClientSettings, Flags, MaxLevel, Theme, TermsAndConditions, RequestedOperation; Ping và UpdateUserProgress mang *Info của event; cả ba mang NewAbData (RegisterResponse chỉ 20 trường: UserProgress, vị trí, RevenueSegment, InstallDate…).
  • Cơ chế delta: PingRequest có 50 trường *Version và UpdateUserProgressRequest có 44. Server trả lại *Info cho mọi event đang chạy (13–14 Info mỗi response lúc chụp) nhưng chỉ Info lệch version mới kèm chuỗi Config. Ví dụ AncientAdventure: client giữ v291 suốt phiên 08/09, Ping 09/09 trả v292 kèm Config.
  • Ngoại lệ tốn băng thông: SeasonalCardCollectionInfo luôn kèm Config (25.723 ký tự) ở cả 21 UpdateUserProgressResponse và mọi PingResponse đã giải mã, vì request không bao giờ gửi SeasonalCardCollectionConfigVersion dù schema có trường này.
  • Config event có hai lớp: ServerEventConfig (chung cho đợt event) và UserEventConfig (cá nhân hoá, về qua Get<Event>Info/Enter). Cả hai lưu trong bảng *TableItem (Id/Value) của DB U_<userid>; config 'hệ thống' như RoyalPassConfig, PinataConfig, SLBMoveConfig, SCOConfig2..7, RemoteRoyalBundles nằm trong KeyValue của DB App; EventDependencyConfig nằm ở LocalKeyValueTable (gắn theo thiết bị).
  • Lưới an toàn offline: 26 file *_default_config.json trong Resources. Các event không có default (AncientAdventure, DailyRewards, SeasonalCardCollection, TeamTournament, MergeSmith, ClashOfChampions, ExpeditionEvent…) chỉ chạy khi đã có config server, nên server tắt được bằng cách không gửi Info.
  • CDN tách khỏi game-server: remote-levels.prod.rylmtch.com (versions + flatbuffer level) và contents.prod.rylmtch.com (dynamic-bundle-config, dynamic-content-config, superlightball-ab, super-charge, magic-duke, ocean-odyssey-levels). Mỗi file có ETag lưu trong KeyValue của App và được kiểm checksum/CRC trước khi dùng.
  • Runtime cho thấy client đã tải sẵn 81 level vá từ xa (tên 7015–14499) dù account mới ở level 8: level vá được đẩy trước, không đợi người chơi tới nơi.
  • Build v38174 không dùng Firebase Remote Config. Chuỗi 'Remote configs will be activated.' thuộc RemoteConfigManager.ActivateRemoteConfigs (tải danh sách level vá + bảng SLB), còn FirebaseHelper chỉ lo analytics, messaging token, AppCheck. Mục này đính chính bảng live-ops trong 06-Social-LiveOps-Analytics.md.

Những điểm bất thường đáng chú ý

  • Seasonal Card Collection gửi lại config cả mùa ở mỗi response: với người chơi đánh nhiều ván, đây là phần nặng nhất của gói UpdateUserProgress (suy luận).
  • PingResponse vẫn chứa AbTestData/AbTestData2/AbTestData3 (bitfield AB đời cũ, ví dụ 8933532008448) và RequestPackage gửi AbTestData = [0, 0, 0]; client v38174 không đọc các trường này, chỉ dùng NewAbData.
  • Schema giữ nhiều trường Deprecated (DeprecatedSegmentOfferInfo, DepreciatedLeagueConfig, DeprecatedLightningRushInfo): FlatBuffers cho phép tiến hoá schema mà không vỡ client cũ, đổi lại response mang 'xác' trường.
  • Version segment tăng đúng 1 giữa 08/09 và 09/09 (RevenueSegmentVersion 1133 → 1134, DynamicOfferUserSegmentVersion 1333 → 1334): gợi ý server tính lại phân khúc theo lô hằng ngày (suy luận).
  • Level vá được đẩy cho mọi người chơi ngay khi mở app (81 file với level 8): dễ vận hành, nhưng tốn tải xuống với người chơi mới chưa cần (suy luận).

Đánh giá

Thang 1–5 (với tiêu chí rủi ro, 5 = rủi ro cao). Trung bình: 3.8.

Tiêu chíĐiểmNhận xét
Hiệu quả băng thông
4/5		Delta theo version cho hơn 40 loại config là chuẩn mực; trừ 1 điểm vì SCC bị gửi lại toàn bộ ở mọi response và level vá đẩy cho cả người mới.
Khả năng chịu offline
4/5		Cache SQLite + 26 default giúp game chạy đủ khi mất mạng; các event không có default sẽ biến mất offline, đây là đánh đổi có chủ đích.
Tốc độ triển khai thay đổi
5/5		Đổi config server có hiệu lực ngay ván kế tiếp qua UpdateUserProgress; đổi level/bảng số qua CDN không cần build.
Khả năng quan sát và gỡ lỗi
3/5		Có log RawData và ForceLog, nhưng config phân tán ở 3 luồng server, 6 file CDN, 2 DB và 4 kiểu bảng; không có 'manifest' hợp nhất cho biết client đang chạy bộ config nào.
Rủi ro cấu hình sai (5 = cao)
3/5		Config server thay hoàn toàn default; checksum chỉ có ở CDN, JSON event chỉ được ValidateConfig ở một số feature (InviteFriends). Một JSON lỗi có thể làm event hỏng tới khi đổi version.
Điểm mạnh
  • Một khuôn chung (Id, RemainingTime, ConfigVersion, Config) cho mọi event giúp thêm event mới mà không đổi luồng tải.
  • Tách config nhẹ (game-server) khỏi nội dung nặng (CDN có ETag) đúng chỗ: số liệu đi nhanh, asset đi chậm và có thể lên lịch.
  • UpdateUserProgress mang luôn *Info nên vòng phản hồi config là theo ván, không phụ thuộc người chơi đóng/mở app.
  • Hai lớp ServerEventConfig / UserEventConfig cho phép cá nhân hoá target/thưởng từng người mà vẫn dùng chung một đợt event.
Điểm yếu
  • SCC thiếu version trong request dẫn tới gửi lặp config cả mùa.
  • Nhiều trường deprecated vẫn nằm trong schema và response.
  • Save SQLite không mã hoá: config và tiến độ đọc/sửa được trên máy root (server vẫn là nguồn sự thật cho level/coin).
Rủi ro
  • Lệch giữa cache cũ và server nếu version bị tái sử dụng: client sẽ không bao giờ tải lại bản sửa.
  • Một file CDN dùng chung cho mọi nhóm AB (superlightball, super-charge): sửa sai một dòng ảnh hưởng toàn bộ nhóm cùng lúc.
  • Event không có default config sẽ mất hẳn khi server sự cố, người chơi có thể mất tiến độ giữa đợt nếu RemainingTime hết.
Đề xuất
  • Gửi SeasonalCardCollectionConfigVersion (hoặc tách phần tĩnh của mùa ra CDN có ETag) để cắt phần lặp lớn nhất của gói tin.
  • Thêm một 'config manifest' trong Ping: danh sách version của mọi config + ETag CDN, client log lại để QA và CS biết chính xác người chơi đang chạy bộ nào.
  • Validate JSON theo schema ở client trước khi ghi đè cache; giữ bản cũ nếu parse lỗi và gửi analytics lỗi config.
  • Chỉ đẩy level vá trong cửa sổ [level hiện tại, level hiện tại + N] cho người chơi mới để giảm tải; người chơi gần đỉnh vẫn nhận toàn bộ.
  • Với game tương tự: dùng đúng khuôn delta-version này cho mọi config, nhưng bắt buộc version tăng đơn điệu và không tái sử dụng.
